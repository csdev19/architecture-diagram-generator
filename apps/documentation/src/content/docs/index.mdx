## Welcome

This is the documentation for **architecture-diagram-generator**: a tool that
treats an architecture diagram as data rather than a drawing. A `DiagramConfig`
JSON document describes groups, nodes and edges, and one pure function renders
it to SVG — so a model can write the document and a person can then refine it by
dragging tiles in the browser.

New here? Start with the [Briefings](/briefings/) — five self-contained answers
to "what is this project?", split by who is asking. For the tool itself, go to
[Diagram Tool](/features/diagram-tool/).

:::caution[Nothing is published yet]
There is no npm package, no release and no deployment. The project runs from a
clone, and the config schema can still change. See the
[Roadmap](/briefings/roadmap) for what is merged versus what is still in review.
:::

## Quick Start

### Prerequisites

- **Bun** `1.3.4` — package manager, script runner and local runtime
- **PostgreSQL** — only for the inherited auth and Todo example; the diagram
  editor does not touch a database

### Installation

```bash
bun install

# copy each app's .env.example -> .env (and .dev.vars for local Worker secrets)
bun run db:push     # only if you want the auth / Todo example working

bun run dev         # every app
```

Then open `/editor`.

:::danger[Environment configuration]
Always use `.env` (and `.dev.vars` for local Worker secrets). **Never** add a
`vars` / `[vars]` / `[env.*]` block to `wrangler.jsonc` — Wrangler auto-loads
`.env`, so a `vars` block drifts from the single source of truth. Run
`wrangler types` after editing a `wrangler.jsonc`. See
[Environment Variables](/environment-variables).
:::

### Scripts

Run these from the repo root; Turborepo fans them out.

```bash
bun run dev                # start all apps
bun run dev:fullstack-fn   # just the web app
bun run build              # build everything
bun run check-types        # typecheck
bun run test               # all tests
bun run test:unit          # domain + application only
bun run test:web           # web-ui + the app's component tests
bun run lint               # oxlint
bun run format             # oxfmt --write
bun run db:push            # push the Drizzle schema
bun run db:studio          # inspect the database
```

:::note[web-ui needs a build]
`@diagram-tool/web-ui` resolves to `src/` under the `development` condition and
to `dist/` otherwise, and `dist/` is git-ignored. `turbo run build` produces it
before the app builds. If you hit "Cannot find module", run `bun run build`
inside `packages/web-ui/`. See [web-ui Package](/web-ui-package).
:::

## Architecture

One TanStack Start app deployed as a **single Cloudflare Worker**. There is no
separate API Worker and no proxy: server-only logic lives in TanStack Start
server functions, and auth runs inside them.

```
architecture-diagram-generator/
├── apps/
│   ├── fullstack-fn-only/     # The app (TanStack Start on Cloudflare Workers)
│   └── documentation/         # This site (Astro Starlight)
│
├── packages/
│   ├── domain/                # Zod schemas, types, constants, the diagram renderer
│   ├── application/           # Use cases (depend only on domain interfaces)
│   ├── infra-db/              # Drizzle schemas, repositories, Neon client
│   ├── infra-auth/            # Better Auth configuration
│   ├── infra-env/             # Zod env schemas
│   ├── config/                # Shared TypeScript config
│   └── web-ui/                # Shared React UI (shadcn/ui + Tailwind)
│
├── docs/                      # Design documents and plans — intent, not status
└── turbo.json
```

**The dependency rule is strict:** `domain <- application <- infra-*`, and only
apps wire them together. `domain` is a leaf, so importing it can never
transitively pull in server code. Full detail in
[Architecture](/architecture/).

For the complete dependency list and the reasoning behind each choice — including
which parts were chosen for the diagram tool and which came with the template —
see the [Stack briefing](/briefings/stack).

## Key Concepts

### The config is the diagram

`DiagramConfig` is a Zod schema in `packages/domain/src/schemas/diagram.ts`. It
validates for the **author**, not the library: messages name the offending value
and the fix, and a single parse reports every problem at once so a model can
correct them all in one retry.

```typescript
import { validateDiagramConfig } from "@diagram-tool/domain/schemas";
import { renderSVG } from "@diagram-tool/domain/render";

const result = validateDiagramConfig(input);
if (result.ok) {
  const svg = renderSVG(result.config);
} else {
  result.errors.forEach((message) => console.error(message));
}
```

### One renderer, everywhere

`renderSVG` is a pure string builder with no DOM and no Node APIs, so the same
function can run in the browser and inside a Worker. Two renderers would let an
exported image disagree with the preview — the exact failure the design exists
to prevent. See [SVG Renderer](/features/diagram-tool/svg-renderer).

### Schema-first everywhere else too

Zod schemas in `packages/domain/` are the source of truth for the rest of the
app as well, reused by server-side validation and client forms alike. See
[Schemas Implementation](/schemas-implementation).
