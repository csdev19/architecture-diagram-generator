## What It Does

Defines what a diagram _is_: a set of boundaries, nodes and edges. Every
surface reads this one contract — the editor validates against it, the renderer
consumes it, and from phase 1 the MCP tool will accept it. Its failure messages
are written for whoever authored the config, so a model that gets a config wrong
can usually fix it without a human stepping in.

### Domain Model

`DiagramConfig` is the aggregate: arrays of `DiagramBoundary`,
`DiagramNode` and `DiagramEdge`. Boundaries and nodes are positioned rectangles;
an edge is a reference between two node ids plus the sides it leaves and enters,
carrying an `id` of its own so nothing has to address it by array position.
All four are plain inferred types — data, no behaviour. A node identifies itself
with either an `iconKey` from the brand registry or an `emoji`; both fields are
optional on their own, and a node-level rule requires at least one of them.

### Key Logic

Field-level rules live on the fields. Everything that needs to see the whole
config — ids being unique, both ends of an edge resolving to real nodes, nodes
— runs in a single `superRefine`, so one parse
reports every problem rather than the first one. Messages name the offending
value and the fix; a dangling edge lists the ids that actually exist.
`validateDiagramConfig` wraps this into either a ready-to-render config or a
list of strings.

## Decisions

| Decision                                                                        | Why                                                                                                                                                                                                                                                             | Alternatives Considered                                                        |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| One `superRefine` for all cross-field rules                                     | A model that receives three errors at once fixes them in one retry; one error per turn burns three turns                                                                                                                                                        | A chain of `.refine()` calls, which stop at the first failure                  |
| Messages state the fix, not the rule                                            | "`edges[3].to`: \"d2\" does not exist. Available nodes: user, hono, d1" is actionable; a raw Zod path is not                                                                                                                                                    | Default Zod messages                                                           |
| Enums come from the constant objects                                            | `z.enum(BOUNDARY_TONES)` keeps one source; re-listing the literals creates a second that drifts                                                                                                                                                                 | Inline string unions                                                           |
| An edge's `id` is optional to write and derived from `from`/`to` when absent    | An author should not have to name something its own endpoints already identify, and everything downstream needs an identity that survives reordering. `deriveEdgeIds` is exported so the editor, which mutates raw JSON, reaches the same edge the schema would | Requiring an id on every edge; or keeping edges positional                     |
| Text fields chain `.trim()` before `.min(1)`                                    | `.min(1)` alone accepts a string of spaces                                                                                                                                                                                                                      | Trimming at the call site                                                      |
| No overlap detection between nodes                                              | A deliberately tight diagram would trip it, and a false rejection is worse than a cramped render. Spacing guidance lives in the authoring guidelines instead                                                                                                    | A hard minimum-distance rule                                                   |
| `emoji` relaxed to optional rather than kept required                           | Requiring both would force a meaningless glyph onto every node that already has a logo. Requiring neither would let a node render blank. One-of-the-two is the only rule that is both honest and safe                                                           | Keeping `emoji` required and treating `iconKey` as decoration                  |
| The emoji-or-iconKey rule sits on the node schema, not the config `superRefine` | It travels with `diagramNodeSchema` wherever a single node is parsed — the editor's field-level mutations in phase 2 included                                                                                                                                   | Adding it to the config-level `superRefine` beside the other cross-field rules |
| Icon keys derive from the registry via `z.enum(DIAGRAM_ICON_KEYS)`              | A hand-written union would drift the moment an icon is added. Zod's own message lists every valid key, which is exactly the correction a model needs                                                                                                            | A `z.string().refine(isValidDiagramIconKey)` with a custom message             |

## Gotchas & Warnings

- ⚠️ The parsed output type differs from the authoring type: defaults mean `DiagramConfig` has fields that `DiagramConfigInput` does not require. Anything hand-writing a config should be typed as the input.
- ⚠️ Coordinates are unbounded, negatives included. There is no canvas to be outside of — the exported frame is derived from the drawing, so nothing is rejected for being too far out. See [ADR 0002](/architecture/decisions/adr-0002-the-frame-is-derived-not-declared).
- ⚠️ `canvas` still exists but is optional, and setting it re-imposes a fixed frame that crops anything outside it. The editor never writes one; leave it out unless an exact size was asked for.
- ⚠️ `background` names a paper tone, never a hex — the renderer owns the value, like every other colour in the format.
- ⚠️ `version` is a literal `1`. A future shape change means a new version and an explicit migration, not a widened schema.
- ⚠️ Whitespace-only text passes `.min(1)` without the `.trim()` in front of it. Every user-facing string field needs both.
- ⚠️ A node carrying **both** `emoji` and `iconKey` is valid, and the renderer draws the icon. The emoji is not a fallback the renderer will ever reach — it only matters if the `iconKey` is later removed by hand.
- ⚠️ `EXAMPLE_DIAGRAM_CONFIG` now uses `iconKey` on two of its three nodes, so it can no longer stand as the regression that pre-icon configs still parse. The schema test keeps a frozen phase-0 literal for that.
