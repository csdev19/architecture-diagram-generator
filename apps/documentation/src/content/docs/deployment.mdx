# Deployment

> **Status: ready to deploy, not yet deployed.** The origin, the pipeline and
> the three secrets it needs are all in place, and the app no longer depends on
> a database — so nothing blocks a release. But no tag has been cut and no
> workflow has run, so nothing on this page claims a deployment that happened.

## The origin

The app is served from **`https://diagrams.cs19.dev`**, a Worker with a custom
domain on a zone that already lives on Cloudflare.

```jsonc
// apps/fullstack-fn-only/wrangler.jsonc
"routes": [{ "pattern": "diagrams.cs19.dev", "custom_domain": true }]
```

Wrangler creates the DNS record on the first deploy. The `cs19.dev` zone has to
be in the same Cloudflare account as the Worker; if it is not, the deploy fails
naming the zone rather than silently serving nothing.

## How a release ships

`main` is the current state of the code. **Production is a tag.** There is no
long-lived `production` branch and promotion is not a merge.

```
merge to main  →  release PR (bot, rolling)  →  merge it  →  tag vX.Y.Z  →  deploy
```

| Workflow                   | Trigger                | Does                                                                                                                           |
| -------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `release-please.yml`       | push to `main`         | Maintains one rolling release PR: accumulates the changelog, recomputes the next version. Cuts nothing until that PR is merged |
| `release-fullstack-fn.yml` | push of a `v*.*.*` tag | Builds and deploys the Worker from the tagged commit                                                                           |

Merging the release PR **is** the act of releasing: it bumps `package.json`,
writes `CHANGELOG.md` and pushes the tag the deployer listens for. The version
that ships is a committed fact in the repo, so the tag and the built artifact
cannot disagree.

The deploy checks out the **tag**, not a branch. Rolling back is therefore
re-running that workflow's run for the older tag from the Actions UI — no revert
commit, no rebuild of a moving target. `workflow_dispatch` on the same workflow
is an escape hatch and behaves differently: it checks out whatever ref you pick,
so it can ship unreleased commits.

### One version line

The repo has exactly one deployable — `apps/fullstack-fn-only` — so the
[closure rule](https://github.com/csdev19/general-knowledge/blob/main/monorepos/release-please-playbook.md)
resolves to a single version line with nothing to intersect. Tags are plain
`vX.Y.Z` with no component prefix.

The workspace packages are not versioned individually and should not be: every
one is consumed through the workspace and none is published, so its version
number would be decoration nobody resolves. Their commits count toward the one
line.

`apps/documentation` is in `exclude-paths` — it has no deploy pipeline, so a
docs-only change should not cut a release.

### Pre-1.0, deliberately

The version line is seeded at **`0.0.0`**, with `initial-version` at `0.1.0` and
`bump-minor-pre-major` on. Nothing has shipped — there has not even been an
alpha — so a `1.0.0` inherited from the monorepo template would have been a
claim about stability that no release supports.

**`bump-minor-pre-major` alone does not achieve this**, and assuming it does
costs you a wrong first release. The schema is precise: _"Breaking changes only
bump semver minor if version < 1.0.0."_ It governs breaking changes and nothing
else. It never had an opinion about what a plain `feat` does.

The setting that matters here is `initial-version`. From `0.0.0` release-please
does not see a version to increment — it sees **no previous release**, and its
default first release is `1.0.0`. That is what it proposed until
`"initial-version": "0.1.0"` was added, which is what actually makes the first
release `v0.1.0`.

Once the line is running, `bump-minor-pre-major` earns its place: while the
major is `0`, a breaking change bumps the minor rather than declaring `1.0.0` by
accident. Declaring `1.0.0` stays a deliberate act — a `Release-As: 1.0.0`
footer in a commit body.

The workspace packages still read `1.0.0` in their own `package.json` files.
That is the template's number and it is inert — nothing resolves it, nothing
publishes them, and only the root package's version is the one release-please
maintains.

### Merge commits are counted twice

A GitHub merge commit's body is the PR title by default:

```
Merge pull request #19 from csdev19/feat/deploy-custom-domain

feat: give the app a production origin at diagrams.cs19.dev
```

That body is a valid conventional commit, so release-please counts it **and**
the original commit it merged. Every PR then appears twice in the changelog —
once under its real commit, once under the merge.

The fix is one repository setting: **Settings ▸ General ▸ Pull Requests ▸
Default commit message → `Blank`** for merge commits (`merge_commit_message:
BLANK` over the API). The merge commit becomes `Merge pull request #19 from …`
with no body, release-please skips it, and the merge-commit history is kept.

Squash merges solve it too, by making one conventional commit per PR — at the
cost of the individual commit messages inside a PR, which this repo uses.

It only affects merges made **before** the setting is changed; those entries are
already in history and can be tidied by editing `CHANGELOG.md` in the release PR
before merging it.

### The token is the part that breaks

`release-please.yml` uses `RELEASE_PLEASE_TOKEN`, a PAT, and not the default
`GITHUB_TOKEN`. GitHub suppresses the events raised by that default token, so a
tag it pushes triggers no workflow: the release PR would open, merge, and tag,
and **nothing would deploy**. That is the single most common way this setup
fails, and it fails silently.

The PAT needs `Contents: read/write` and `Pull requests: read/write` on this
repo, stored in the `production` environment.

## Secrets

Both workflows read from the `production` environment.

| Secret                  | Used by                    | For                                        |
| ----------------------- | -------------------------- | ------------------------------------------ |
| `RELEASE_PLEASE_TOKEN`  | `release-please.yml`       | Opening the release PR and pushing the tag |
| `CLOUDFLARE_API_TOKEN`  | `release-fullstack-fn.yml` | Authenticating the deploy                  |
| `CLOUDFLARE_ACCOUNT_ID` | `release-fullstack-fn.yml` | Naming the account to deploy into          |

Three, and that is the whole list. **Nothing is uploaded to the Worker**: the
app is the editor, the editor runs in the browser, and no code path reads the
environment at runtime. There is no secret that can be missing, which is a
property worth keeping — the moment one comes back, so does a class of failure
where the deploy succeeds and the first request throws.

The two Cloudflare values are deploy credentials, not Worker secrets: the app
never reads them, and shipping them into its runtime would hand it the key to
redeploy itself.

## Why a subdomain and not `cs19.dev/editor`

`cs19.dev` is a separate static site, already on Cloudflare, and `/editor` on it
is a free path. This decision was made when the app still carried the template's
auth stack, and **two of its four arguments died with that stack** — an honest
accounting matters more than a tidy one:

| Argument                                                             | Still holds?                                                                |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| The app owns six route prefixes, each to be won from the static site | **No.** It owns one route now                                               |
| The session cookie would be scoped to the apex                       | **No.** There is no session and no cookie                                   |
| A bad deploy here would share a request namespace with `cs19.dev`    | **Yes.** A wrong pattern still takes down the home page                     |
| The address should be one the project can keep                       | **Yes.** A path is on someone else's site; a hostname moves with a redirect |

What replaces the first argument is smaller but real: an app served from a path
needs a Vite `base` and a router `basepath`, because it still requests
`/assets/*` and its server-function endpoints from the root. That is
configuration to write, verify and undo later — not much, but not nothing, and
bought with the two arguments above still against it.

So the conclusion is unchanged and the reasoning behind it is now thinner. If
the trade ever reverses — the editor becomes a section of a personal site rather
than a product — the honest move is to reopen this, not to defend it.

## Why not the `workers.dev` URL

It is not less reliable — same edge, same certificate, same uptime. It is a bad
_public_ address for three other reasons: it reads as a scratch URL to whoever
you send it to, `*.workers.dev` is blocked by some corporate DNS filters, and
the address cannot move with the project.

It stays useful as the preview target. Production is the custom domain.

## `BETTER_AUTH_URL` must name this exact origin

better-auth builds its callback and cookie domain from `BETTER_AUTH_URL`. It has
to be `https://diagrams.cs19.dev` in production, and changing the hostname later
means changing this variable and invalidating every live session — which is the
practical reason the address was chosen before the first deploy rather than
after.

Set it, like every other variable, in `.env` (and `.dev.vars` for local Worker
secrets). Never add a `vars` block to `wrangler.jsonc`: Wrangler auto-loads
`.env`, and a second copy in the config drifts from it.

Secrets — `DATABASE_URL`, `BETTER_AUTH_SECRET`, `JWT_PRIVATE_JWK` — are uploaded
with `wrangler secret put`, not committed anywhere.

## What the app is, and why nothing blocks the deploy

The app is one route — the editor — and it is a client-side canvas. It parses,
resolves and renders a diagram in the browser; the Worker's whole job is to
serve the document and the assets.

That is what unblocked this. The blocker used to be the database: the template
shipped a home page, sign-in and sign-up, a Todo CRUD example and better-auth
over Postgres, and a Worker cannot open a TCP connection to Postgres. So the
deploy would have produced something that served the editor and threw on
everything else.

Removing the site removed the blocker rather than working around it. There is no
`DATABASE_URL`, no auth, no server-side session, no `fullstackServerEnvSchema` to
satisfy. The Worker reads nothing from its environment, so it cannot be deployed
into a broken state by a secret nobody set.

The database packages — `infra-db`, `infra-auth`, the Todo use cases — are still
in the repo. Nothing imports them from the app any more, and the day one is
needed again, whichever option below is chosen has to be chosen deliberately:

| Option                     | What it would change                                                            |
| -------------------------- | ------------------------------------------------------------------------------- |
| Neon or Supabase over HTTP | A serverless driver replaces the node-postgres client                           |
| Hyperdrive                 | Cloudflare pools the connection behind a binding                                |
| Cloudflare D1              | The dialect becomes SQLite — the largest change, and it touches every migration |

## Before the first release

Nothing here has run. In order:

1. **Store the three secrets** in the `production` environment:
   `RELEASE_PLEASE_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`.
2. **Land a `feat` or `fix` on `main`.** A batch of only `chore`/`docs`/`ci`
   commits is not releasable and no release PR appears — that is correct
   behaviour, not a broken bot.
3. **Check the release PR** opens with a sane version and a changelog containing
   only commits since `bootstrap-sha`. Opening a PR ships nothing, so this step
   is free.
4. **Merge it, and confirm the tag exists** and that
   `release-fullstack-fn.yml` actually started. A tag with no workflow run means
   the token is wrong — that is the failure to expect.
5. **Re-run that deploy run once** from the Actions UI, to prove rollback works
   before you need it.

The old `deploy-production.yml`, which triggered on a `production` branch, is
deleted. It never ran — the branch was never created — so removing it closed no
path to production that existed.
